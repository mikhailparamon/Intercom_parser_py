# Intercom Conversation Exporter

CLI-приложение на Python для выгрузки обращений Intercom вместе с доступной историей переписки в форматированный JSON и подготовки отчёта по поддержке через OpenRouter или Dahl API либо вручную через ChatGPT.

## Требования

- Python 3.11 или новее
- Git
- Intercom access token с разрешением на чтение обращений

## Установка (Windows PowerShell)

Из каталога проекта выполните:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Если PowerShell запрещает активацию окружения, можно вызывать Python напрямую: `\.venv\Scripts\python.exe`.

В CMD активация выполняется так:

```cmd
.venv\Scripts\activate.bat
python -m pip install -r requirements.txt
copy .env.example .env
```

## Установка (Linux)

Нужен Python 3.11 или новее и Git. Для Debian/Ubuntu установите системные пакеты:

```bash
sudo apt update
sudo apt install -y git python3 python3-venv python3-pip
python3 --version
```

Если `python3 --version` показывает версию ниже 3.11, установите Python 3.11+ средствами своего дистрибутива и далее указывайте соответствующую команду, например `python3.11`.

Перейдите в каталог проекта, создайте виртуальное окружение и установите зависимости:

```bash
cd intercom-conversation-exporter
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
cp .env.example .env
```

Команды активации подходят для Bash и Zsh. Чтобы выйти из окружения, выполните `deactivate`.

Проверьте, что установлен Python 3.11+ и Git. Если их нет, установите Homebrew с [официального сайта](https://brew.sh/), затем выполните:

Создайте виртуальное окружение, установите зависимости и скопируйте шаблон настроек:

## Настройка `.env` на Linux и macOS

Заполните `.env` по разделу «Настройка Intercom» ниже. Перед реальной выгрузкой проверьте параметры без обращения к API:

python main.py --dry-run

## Настройка Intercom

Создайте private app в Intercom Developer Hub и возьмите access token в Configure → Authentication. Для этого инструмента используйте токен только своего рабочего пространства; не публикуйте его и не передавайте третьим лицам. Подробности есть в [официальной документации Intercom по авторизации](https://developers.intercom.com/docs/build-an-integration/learn-more/authentication).

Откройте `.env` и заполните параметры:

```dotenv
INTERCOM_ACCESS_TOKEN=ваш_токен
INTERCOM_API_VERSION=2.17
OPENROUTER_API_KEY=
OPENROUTER_MODEL=anthropic/claude-sonnet-4.5
OPENROUTER_WORKERS=3
DAHL_API_KEY=
DAHL_MODEL=MiniMaxAI/MiniMax-M2.7
DAHL_WORKERS=3
```

Токен Intercom не принимается через CLI, не попадает в экспорт или manifest и не выводится в логах. `OPENROUTER_API_KEY` обязателен для `--analyze openrouter`, `DAHL_API_KEY` — для `--analyze dahl`; оба ключа необязательны, потому что без флага `--analyze` программа только создаёт входные файлы и промпт для ручного анализа. `OPENROUTER_MODEL` можно изменить на другую модель OpenRouter. `OPENROUTER_WORKERS` задаёт число одновременных запросов (от 1 до 10, по умолчанию 3); для бесплатных моделей начните с 2–3 и уменьшите значение, если провайдер отвечает HTTP 429. `DAHL_MODEL` задаёт модель Dahl (по умолчанию `MiniMaxAI/MiniMax-M2.7`), `DAHL_WORKERS` — число одновременных запросов (от 1 до 10, по умолчанию 3). `.env`, каталоги результатов, логи и виртуальное окружение исключены через `.gitignore`; не добавляйте ключи в Git.

## Использование

Запуск без параметров включает режим мониторинга. Он выгружает полный набор полей Intercom для обращений с активностью за скользящую неделю — ровно последние 7×24 часа от момента запуска, — и выделяет из неё срез за скользящие сутки (ровно последние 24 часа). Например, при запуске 2 ноября 2026 года в 08:00:00 UTC неделя охватывает `[2026-10-26T08:00:00Z, 2026-11-02T08:00:00Z)`, а день — `[2026-11-01T08:00:00Z, 2026-11-02T08:00:00Z)`. С флагом `--full-archive` вместо недели выгружается архив за последние три месяца, и оба среза выделяются из него. Начало трёхмесячного периода ограничивается последним днём целевого месяца, если исходный день там отсутствует.

```powershell
python main.py
```

Проверить мониторинговые интервалы без обращения к API:

```powershell
python main.py --dry-run
```

Прежний режим экспорта с произвольным периодом запускается через `--standard`:

```powershell
python main.py --standard --start 2026-07-01 --end 2026-10-01
```

Без `--start` и `--end` обычный экспорт выгружает скользящую неделю — ровно последние 7×24 часа от момента запуска.

Проверить обычный экспорт без обращения к API:

```powershell
python main.py --standard --start 2026-07-01 --end 2026-10-01 --dry-run
```

По умолчанию детали обращений запрашиваются в 15 потоков. При необходимости параллелизм можно изменить, например `--workers 6`; слишком большое значение может привести к ответам API `429` и задержкам на повторных запросах.

Параметры CLI:

| Параметр | Описание |
| --- | --- |
| `--standard` | Запустить прежний экспорт вместо мониторинга. Только в этом режиме доступны `--start`, `--end`, `--selection` и `--fields`. |
| `--full-archive` | Мониторинг: выгружать архив за последние три месяца вместо недели; оба среза выделяются из архива. |
| `--start YYYY-MM-DD` | Начальная календарная дата UTC, включительно; используется вместе с `--standard` и `--end`. |
| `--end YYYY-MM-DD` | Конечная календарная дата UTC, исключительно; используется вместе с `--standard` и `--start`. |
| `--output PATH` | Корневой каталог результатов; по умолчанию `data`. |
| `--workers N` | Максимальное количество одновременных запросов деталей; по умолчанию `15`, должно быть не меньше `1`. |
| `--selection {new,updated,all}` | Тип обращений в обычном режиме; по умолчанию `all`. Мониторинг всегда использует `all`. |
| `--fields {important,all}` | Набор полей в обычном режиме; по умолчанию `important`. Мониторинг всегда использует `all`. |
| `--timezone TIMEZONE` | Формат временных полей: `UTC` (по умолчанию), имя IANA, например `Europe/Moscow`, или `unix` для исходных Unix-значений. |
| `--dry-run` | Печатает мониторинговые интервалы или период обычного экспорта, не читает токен и не вызывает API. |
| `--skip-analysis` | Не подготавливает файлы и не запускает автоматический AI-анализ после экспорта. |
| `--analyze {openrouter,dahl}` | Автоматический AI-анализ после экспорта через выбранный провайдер; без флага готовятся только файлы для ручного анализа. |
| `--verbose` | Подробное логирование без тел обращений и заголовков авторизации. |

Мониторинг без `--full-archive` выполняет один запрос полного набора за скользящую неделю с `selection=all` и `fields=all`, затем формирует из него локальный срез дня по времени создания и содержательных частей переписки. С `--full-archive` запрос выполняется за три месяца, и оба среза выделяются из архива. Результаты находятся в уникальной папке запуска: `last_week/` и `last_day/` (плюс `backup_3_months/` при `--full-archive`); в каждой лежат `conversations.json` и `manifest.json`.

Для AI-анализа создаётся одна папка `support-analysis/` с `chatgpt_input_week.json`, `chatgpt_input_day.json` и одним `PROMPT.md`. Промпт требует классифицировать общий набор уникальных ID один раз, а выводы подготовить для каждого окна отдельно. Дневной набор входит в недельный, поэтому их частоты нельзя складывать. Если один срез пуст, его JSON всё равно создаётся, когда другой срез содержит обращения. `--skip-analysis` отключает подготовку, но не создание срезов.

При частичном экспорте доступные обращения сохраняются и используются для срезов; статус `partial` и ошибки исходного экспорта отражаются в манифестах. В обычном режиме `--standard` автоматически подготавливается анализ полной выгрузки, как и раньше.

Дата окончания должна быть позже даты начала. Для дат `[2026-07-01, 2026-10-01)` период включает события начиная с полуночи 1 июля и до полуночи 1 октября UTC.

## Правило отбора и история

`--selection` определяет, какие обращения попадут в выгрузку:

- `new` — обращения, созданные внутри выбранного периода;
- `updated` — обращения, созданные до начала периода и имеющие внутри него осмысленную активность;
- `all` — объединение новых и обновлённых старых обращений.

Для дат `[2026-07-01, 2026-10-01)` начало включается, конец исключается; все временные границы рассчитываются в UTC. Осмысленной активностью считаются создание обращения и содержательные части переписки (`comment`, `open`, `note`, `close`); системные события (`bulk_reassignment`, `assignment`, `conversation_attribute_updated_by_admin`, `snoozed`, `timer_unsnooze` и т.п.) и само по себе поле `updated_at` обращение в выборку не включают — это отсекает всплески от массовых админских операций, которые обновляют `updated_at` тысяч обращений разом без единого сообщения от клиента.

После включения обращения сохраняются все доступные части его истории, в том числе созданные до начала и после конца периода. Сам период определяет отбор обращения, а не обрезает его историю.

Приложение использует `POST /conversations/search` с пагинацией и фильтрами-кандидатами по `created_at` и `updated_at`, затем локально проверяет время создания и содержательных частей переписки. Чтобы найти старое обращение, которое продолжили в периоде, поиск может вернуть также обращения, обновлённые после конца периода; окончательное решение принимается по точным временным границам. Детали получает через `GET /conversations/{id}`. Версия API передаётся в заголовке `Intercom-Version`.

### Ограничение Intercom

Документация Intercom указывает жёсткий предел в 500 частей переписки на один retrieve: API возвращает до 500 наиболее новых частей. Счётчик частей используется для обнаружения усечения. Если период активности невозможно проверить по усечённой истории, manifest отмечает выгрузку как `partial`; часть продолжений может быть не обнаружена. Этот предел нельзя обойти клиентской пагинацией. См. [поиск обращений](https://developers.intercom.com/docs/references/rest-api/api.intercom.io/conversations/searchconversations), [схему части переписки](https://developers.intercom.com/docs/references/rest-api/api.intercom.io/models/conversation_part) и [получение обращения](https://developers.intercom.com/docs/references/rest-api/api.intercom.io/conversations/retrieveconversation).

## Файлы результата

Мониторинг сохраняет запуск в `data/<start>_<end>_run_<UTC-время>/`; повторные запуски не перезаписывают предыдущие. В обычном режиме результаты находятся в `data/<start>_<end>/`, а повторный запуск получает уникальный суффикс.

- `conversations.json` — UTF-8, форматированный JSON-массив обращений;
- `manifest.json` — период, время запуска, выбранные `selection` и `fields`, длительность экспорта в секундах (`elapsed_seconds`), версия API, число обращений, ошибок, статус и известные ограничения. В мониторинге эти файлы лежат в каждой папке-срезе (две без `--full-archive`, три с ним); манифест архива также сохраняет метаданные исходного экспорта.

По умолчанию `--fields important` сохраняет `id`, `title`, `created_at`, `updated_at`, текст начального сообщения (`source.body`) и текст частей переписки. Для каждой части остаются `part_type`, `created_at` и тип автора, чтобы различать сообщения клиента, ответы оператора и системные события. Контакты, идентификаторы авторов, вложения и остальные служебные поля исключены. `--fields all` сохраняет весь объект, который вернул Intercom для обращения, вместе со всеми вложенными полями и исходной структурой API.

После завершения CLI и в логе показывается длительность в формате `часы минуты секунды`, например `0 ч 0 мин 5 сек`. Секунды округляются до ближайшего целого. Длительность измеряется монотонными часами от начала выгрузки до сохранения JSON.

При `--fields all` сохраняются все поля, фактически возвращённые API, включая email и другие персональные данные, если они есть в ответе. Структура `conversation_parts` сохраняется без преобразований. Этот режим может содержать конфиденциальную информацию.

Временные поля в обоих режимах по умолчанию преобразуются в ISO 8601 UTC с суффиксом `Z`, например `"created_at":"2026-10-27T11:56:00Z"`. Укажите IANA-зону, чтобы получить её местное время с UTC-смещением; преобразование учитывает сезонные переходы. `--timezone unix` оставляет временные поля числами, как их вернул Intercom. Выбранный режим записывается в `manifest.json`; время запуска `started_at` всегда сохраняется с UTC-смещением.

Примеры выбора часового пояса в обычном режиме:

```powershell
python main.py --standard --start 2026-07-01 --end 2026-10-01 --timezone Europe/Moscow
python main.py --standard --start 2026-07-01 --end 2026-10-01 --fields all --timezone unix
```

Каждый запуск записывается в собственную папку. До полной сборки JSON во временном файле результат текущего запуска не появляется; прежние каталоги и файлы остаются без изменений.

`status` manifest будет `success`, если не было ошибок или обнаруженного усечения истории, и `partial`, если API-запросы завершились ошибкой или выявлено ограничение частей переписки. При сбое выгрузка не считается полной.

## Анализ обращений через OpenRouter, Dahl или ChatGPT

Автоматический анализ по умолчанию выключен: каждый запуск готовит файлы для ручного анализа (если не задан `--skip-analysis`), но не обращается к внешней модели. Флаг `--analyze openrouter` включает автоматический анализ через OpenRouter (нужен `OPENROUTER_API_KEY` в `.env`), а `--analyze dahl` — через Dahl (нужен `DAHL_API_KEY`; endpoint `https://inference.dahl.global/v1`, модель по умолчанию `MiniMaxAI/MiniMax-M2.7` задаётся переменной `DAHL_MODEL`, параллелизм — `DAHL_WORKERS`, от 1 до 10, по умолчанию 3). После подготовки очищенных JSON программа вызывает выбранный провайдер. Данные разбиваются на пакеты размером до 400 КБ по UTF-8 и классифицируются с ограниченной параллельностью; затем отдельный короткий запрос объединяет выводы пакетов. Проверенные результаты пакетов сохраняются в `support-analysis/.openrouter-cache/`, поэтому повторная подготовка с тем же входом и тем же каталогом анализа использует готовые пакеты и продолжает после места сбоя. Для мониторинга общий уникальный набор ID классифицируется один раз, а выводы отдельно собираются для недели и дня. Результат сохраняется в `chatgpt_result.json`, затем программа проверяет ID, полноту и схему и локально создаёт `report.md` и `classifications.csv`.

Провайдер анализа получает только подготовленные JSON и промпт, а не полный экспорт Intercom. В текстах удаляются найденные email, телефоны, секреты, URL и типовые подписи; ID и имена остаются. Очистка по шаблонам не гарантирует удаления всех персональных данных, поэтому проверяйте входные JSON перед использованием. Запросы могут тарифицироваться по модели и объёму токенов.

Без флага `--analyze` анализ не запускается, но файлы для ручной загрузки создаются как обычно:

```powershell
python analyze_support.py prepare --input data/2026-10-27_2026-10-30/conversations.json
```

В обычном режиме `--standard` появятся `support-analysis/chatgpt_input.json` и инструкция `support-analysis/PROMPT.md`.

В режиме мониторинга загрузите в ChatGPT Work оба файла `support-analysis/chatgpt_input_week.json`, `support-analysis/chatgpt_input_day.json` и общий `support-analysis/PROMPT.md`. Сохраните единый результат как `support-analysis/chatgpt_result.json`. Он должен содержать по одной классификации на уникальный ID и отдельные сводки для недели и дня.

Проверить результат и локально создать единые `report.md` и `classifications.csv` можно командой:

```powershell
$runDir = "data\2026-07-31_2026-10-31_run_<UTC-время-запуска>"
python analyze_support.py report-monitoring --week "$runDir\last_week\conversations.json" --day "$runDir\last_day\conversations.json" --result "$runDir\support-analysis\chatgpt_result.json"
```

Вместе с `report.md` и `classifications.csv` команда `report-monitoring` генерирует интерактивный офлайн-дашборд `dashboard.html` (KPI, график обращений по дням, круговые диаграммы категорий за неделю и день, топ-10 подкатегорий, распределение тяжести, таблица обращений высокой тяжести). Дашборд строится детерминированно из проверенных классификаций, без обращения к LLM. По умолчанию файл пишется в общий каталог анализа; каталог можно переопределить флагом `--dashboard-dir`:

```bash
python analyze_support.py report-monitoring --week .../last_week/conversations.json --day .../last_day/conversations.json --result .../chatgpt_result.json --dashboard-dir "D:\Program\My projects\Intercom\report_dashboard"
```

Запустить автоматический анализ без нового экспорта можно флагом `--analyze` у команд `prepare` и `prepare-monitoring`:

```powershell
python analyze_support.py prepare-monitoring --week "$runDir\last_week\conversations.json" --day "$runDir\last_day\conversations.json" --output "$runDir\support-analysis" --analyze dahl
```

Без `--analyze` команды `prepare` и `prepare-monitoring` только готовят файлы для ручного анализа; с `--analyze` без ключа соответствующего провайдера в `.env` команда завершается с ошибкой. Если автоматический анализ остановился, та же команда повторно подготовит и продолжит его в том же каталоге, используя проверенные пакеты из кэша.

Команда проверит полноту объединения, fingerprints обоих окон и членство ID, затем создаст один отчёт с отдельными рейтингами для недели и дня и сравнительной таблицей. Совпадающие ID классифицируются один раз; в CSV указывается, к каким окнам относится каждое обращение. Для повторной подготовки пары входов без нового экспорта используйте `analyze_support.py prepare-monitoring --week ... --day ... --output ...`.

Анализ использует фиксированную таксономию из 10 категорий с правилами границ (см. `support_analysis_prompt_template.md`, раздел 3).

**Быстрый старт исследования — две команды без путей:**

```powershell
python main.py                      # 1. выгрузка за неделю и день + очистка + пакет оркестрации субагентов
python analyze_support.py research  # 2. проверка оркестрации → слияние → отчёт + дашборд
```

По умолчанию `prepare-monitoring` дополнительно готовит пакет оркестрации субагентов (`agents_work/`: чанки, `taxonomy.json`, `manifest.json`, `agents_protocol.md`). Дальше агент-оркестратор поднимает субагентов по манифесту (каждый классифицирует свой чанк по `agents_protocol.md`), после чего:

```bash
python analyze_support.py merge-agents --week .../last_week/conversations.json --day .../last_day/conversations.json [--compare-with предыдущий/chatgpt_result.json]
```

`merge-agents` валидирует результаты (покрытие ID, дубликаты, категории из таксономии), собирает `chatgpt_result.json`, строит `report.md` и `dashboard.html`, а с `--compare-with` — `comparison_report.md`. Общие рекомендации (один блок для отчёта и дашборда, без разбивки по периодам) передаются файлом JSON со списком строк: `--recommendations путь/recommendations.json` (без флага автоматически подхватывается `agents_work/recommendations.json`, если он есть). Если рекомендации не переданы, они выводятся детерминированно из статистики классификаций — топ-3 категорий, числа обращений высокой тяжести и доли обращений без оценки тяжести, — поэтому отчёт и дашборд всегда содержат раздел рекомендаций. Команды `merge-agents` и `render-dashboard` работают без путей: по умолчанию берётся последний прогон в `data/`; конкретный прогон — `--run <каталог>`, либо явные `--week`/`--day`. Отключить пакет: `--no-agents`. Число субагентов: `--workers N` (по умолчанию 10). Режимы `--analyze openrouter|dahl` остаются альтернативой.

Единый запуск без путей: `python analyze_support.py research`. Команда находит последний прогон в `data/`, при необходимости создаёт пакет оркестрации, проверяет готовность результатов воркеров (код возврата 3 — «запустите субагентов и повторите»; в среде Kimi субагентов поднимает агент-оркестратор) и после оркестрации выполняет слияние с автоподхватом `agents_work/recommendations.json` и построение дашборда. После `python main.py` пакет оркестрации создаётся автоматически (отключить: `--no-agents`). Число субагентов задаётся `--agent-workers N` (main.py), `--workers N` (prepare-monitoring, research) или переменной `AGENT_WORKERS` в `.env` (по умолчанию 10, диапазон 2–20). Отдельные шаги: `prepare-monitoring` (очистка), оркестрация по манифесту, `merge-agents`, `render-dashboard` (дашборд из готового `chatgpt_result.json`).

Если среда агента **не умеет порождать субагентов** (например, Codex), параллельную оркестрацию выполнить нельзя. В этом случае агент должен классифицировать чанки **по очереди сам**: для каждого `agents_work/chunk_XX.json` прочитать его, классифицировать все обращения по `PROMPT.md` и записать `agents_work/result_XX.json` в формате протокола, затем запустить `merge-agents`. Держите в одном контексте один чанк за раз (не накапливайте несколько), иначе контекст переполнится; после записи каждого `result_XX.json` контекст чанка можно забывать. Режим `--analyze openrouter|dahl` остаётся альтернативой, когда API-провайдер доступен (параллелизм обеспечивается самим Python-скриптом).

Анализатор читает новый формат `conversations.json` и поддерживает старые выгрузки `conversations.jsonl`.

Размер пакетов ограничивает нагрузку на контекст, но для наборов до 10 000 записей потребуется много API-запросов; их доступность зависит от лимитов модели и аккаунта, а платные модели тарифицируют каждый пакет и итоговый синтез. Временные ошибки сети и HTTP 408/429/5xx повторяются с задержкой; пустой ответ сопровождается причиной завершения генерации, моделью и числом выходных токенов, если провайдер их вернул. Если отдельное обращение превышает безопасный лимит 750 КБ, API-анализ останавливается, а входы остаются для ручной обработки. При ошибке API или неполном ответе отчёт не создаётся. Локальная проверка сверяет число обращений, все ID и fingerprint исходного набора.

Сохраните скачанный JSON как `support-analysis/chatgpt_result.json`. При желании проверьте и пересоздайте `report.md` и `classifications.csv` локально по валидированной классификации:

```powershell
python analyze_support.py report --input data/2026-10-27_2026-10-30/conversations.json --result data/2026-10-27_2026-10-30/support-analysis/chatgpt_result.json
```

Команда создаст `report.md` для руководителя и `classifications.csv` с классификацией каждого обращения. Частоту по категориям и распределение тяжести считает программа по уникальным ID, а не берёт из текстовых оценок ChatGPT. Если классификация неполная, содержит неизвестные или дублированные ID либо категории/уровни тяжести не соответствуют схеме, отчёт не создаётся.

Перед подготовкой скрипт удаляет из заголовков и текста найденные email, телефонные номера, секреты по распространённым шаблонам, URL и типовые подписи. Остальной текст и исходные ID сохраняются. Просмотрите JSON до передачи внешней модели. Файлы подготовки и результата содержат текст обращений и исключены из Git, если находятся внутри `data/`.

## Ошибки и повторные запросы

- Ошибки авторизации HTTP 401/403 не повторяются.
- HTTP 429 и временные HTTP 5xx повторяются ограниченное число раз с экспоненциальной задержкой; учитывается `Retry-After`.
- Сетевые ошибки и тайм-ауты повторяются ограниченное число раз.
- Цикл курсорной пагинации обнаруживается и завершает обработку с ошибкой.
- В логах нет текстов переписок, токена или заголовков запроса.
- Для частичного результата manifest содержит статус `partial` и число ошибок.

## Частые проблемы

- **Не задан `INTERCOM_ACCESS_TOKEN`** — проверьте `.env`; `.env.example` является только шаблоном.
- **HTTP 401/403** — проверьте токен, workspace приложения и доступ к чтению разговоров.
- **HTTP 429 или временная ошибка сервера** — клиент автоматически выполнит ограниченные повторы; при исчерпании повторов экспорт будет отмечен как частичный.
- **`partial` при большом разговоре** — retrieve Intercom ограничен 500 самыми новыми частями.
- **Неверные даты** — задавайте обе даты в `YYYY-MM-DD`; конец должен быть позже начала.

## Конфиденциальность

Экспорт содержит клиентские сообщения и чувствительные данные. Храните каталог результатов с соответствующими ограничениями доступа, не добавляйте его в Git и удаляйте по политике хранения вашей организации. Утилита не выполняет реальных запросов, пока пользователь не укажет токен в `.env` и сам не запустит обычный режим CLI.
