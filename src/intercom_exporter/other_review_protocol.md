# Повторная проверка категории «Прочие обращения»

Это отдельный проход с новым контекстом. Вход — только `{chunk_path}`, политика — `{prompt_path}`, таксономия — `{taxonomy_path}`, выход — `{result_path}`. Предыдущая классификация не является эталоном.

Для каждого ID прочитай всю очищенную переписку и содержательный заголовок, а не только первое сообщение. Найди собственные слова клиента, склей короткие реплики и восстанови смысл подтверждённых ответов на вопросы оператора. Отдели актуальный запрос от прошлых цитат, /start, приветствия бота, подписей и типовых инструкций поддержки. Информативный заголовок может содержать весь запрос, даже когда тело письма пусто.

Обязательно проверь: вход/код, подключение, доступ к сайтам/YouTube, скорость, ключ/конфигурация, оплата, отмена/возврат/продление, установка/обновление, совместимость и вопросы о сервисе. Нет диагноза или подробностей — не основание для «Прочих»: выбирай установленную категорию, подкатегорию «Проблема не уточнена» и осторожную уверенность. Платформу указывай отдельно. Не переноси назначение по одному ключевому слову и не подменяй чтение переписок скриптом с fallback в «Прочие».

Контрольные случаи (формулировки ниже объясняют смысл; subcategory_code и точное название бери из закрытого справочника схемы 2, а не из свободного описания примера):
- «Не получается войти» → категория авторизации / «Ошибка входа», неизвестный способ входа не мешает определить тему.
- «Как поменять карту для оплаты?» только в title → оплата и подписка / «Смена платёжной карты».
- «Можете повторно отправить ключ для OpenVPN?» → VPN: ключи и конфигурации / «Повторная выдача ключа».
- «Верните деньги, перестало работать» → оплата и подписка / «Возврат денег», техническая проблема — дополнительная тема.
- «Подписка активна, но YouTube пишет нет интернета» → проблема доступа / «Нет подключения к интернету».
- «Оплатил» отдельно не доказывает сбой оплаты; /start отдельно не доказывает техническую проблему.
- Подтверждённая проблема остаётся тематической, даже если в конце клиент сказал «спасибо» или сообщил, что всё заработало.

Используй только subcategory_code из taxonomy.json и точное название из справочника PROMPT.md. Для схемы 2 «Прочие обращения» имеют только no_request / «Нет содержательного запроса» или non_target / «Автоматическое, нецелевое сообщение или спам». Причину такого решения объясни в review_reason. Не ставь количественную цель снижения доли «Прочих» и не выдумывай запрос за клиента. Старые задания схемы 1 допускают прежние основания.

Верни JSON: `{"review_fingerprint": "<точно из чанка>", "classifications": [...]}`. Ровно одна классификация на каждый ID чанка, никаких чужих ID. Поля: id, category, subcategory, additional_topics (массив), platforms (массив), problem_summary, severity (low/medium/high/null), severity_reason, confidence (low/medium/high), evidence (точная короткая цитата клиента или содержательного title), review_reason (почему выбрана эта категория после проверки всей переписки). Для тематической категории evidence обязательно и должно дословно встречаться во входе. Для оставшихся «Прочих» подробно укажи основание в review_reason. Сохраняй исходные ID и отпечаток без изменений. Перед завершением проверь покрытие ID программно.
